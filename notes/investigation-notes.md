
# Investigation Notes — Zeek Lab 06

## 1. Investigation Summary

This investigation focused on creating and testing a custom Zeek detection that generates a notice when a TCP connection targets destination port `8765`.

The analysis reused `beaconing-investigation.pcap` from the previous lab. The capture contains controlled HTTP traffic between localhost endpoints and provides a repeatable dataset for validating the detection.

The primary objective was to determine whether Zeek could identify the specified connection condition and record it in `notice.log`.

## 2. Evidence Reviewed

| Evidence | Purpose |
|---|---|
| `beaconing-investigation.pcap` | Offline network traffic used to test the rule |
| `first-detection.zeek` | Custom detection script |
| `conn.log` | Connection metadata and destination ports |
| `http.log` | HTTP requests and responses |
| `notice.log` | Alerts generated by the custom detection |
| `files.log` | File-analysis records generated by Zeek |
| `packet_filter.log` | Packet-filter information |

## 3. Detection Implementation

The script loads Zeek's notice framework and defines the custom notice type `Test_Port_Connection`.

The `connection_state_remove` event checks whether the connection's destination port matches TCP/8765. If the condition matches, the script calls `NOTICE()` with the custom notice type, a descriptive message, and the associated connection record.

The message includes the origin address and port to provide useful context for subsequent investigation.

## 4. Observed Findings

- Eight connections to TCP/8765 were recorded in `conn.log`.
- The origin and responder addresses were both `127.0.0.1`.
- The connections were identified as HTTP traffic.
- The connection records showed state `SF`.
- Six custom detection notices were recorded in `notice.log`.
- The notices used `FirstDetection::Test_Port_Connection`.
- The notice messages identified the source port and monitored destination port.

## 5. Detection Coverage Review

The observed evidence confirms that the script generated notices for some matching traffic. It does not establish that every matching connection generated a notice.

The connection log contains eight records, while the notice log contains six. The supplied notice timestamps correspond to the second through seventh connection timestamps. The first and eighth connection timestamps do not appear in the supplied notice output.

Compare the connection UIDs, timestamps, and notice records to investigate the discrepancy. The available evidence does not establish its cause.

## 6. Assessment

The custom script demonstrated that Zeek can evaluate connection metadata and produce structured notices from an offline PCAP.

The rule is useful as a basic detection-engineering exercise. In a real environment, a port-based match should be assessed alongside destination asset information, expected services, connection frequency, and other relevant network evidence.

The input capture contains controlled localhost traffic. The observed port match does not establish malicious activity.

## 7. Conclusion

The script generated custom notices, demonstrating the basic detection workflow. However, the difference between eight connection records and six notices remains unresolved.

The detection is functionally demonstrated but should not be considered fully validated for coverage until the discrepancy has been investigated. Further testing should establish why two connection records did not produce visible notices and confirm the rule's behavior across different traffic conditions.
